# Отчёт по проекту Catalogio

## Доменная область

Catalogio — персональный каталог контента. Пользователь ведёт список фильмов, сериалов, книг и игр: задаёт им тип, статус, оценку, описание и заметки.

## Стек реализации

- Go 1.27, стандартная библиотека `net/http`
- PostgreSQL 18
- pgx
- HTML, CSS и JavaScript
- Docker и Docker Compose
- golang-migrate

## Основные сущности

- `User` — владелец персонального каталога.
- `Item` — единица контента с названием, описанием, статусом, типом, оценкой и заметками.
- `ItemType` — тип контента: фильм, сериал, книга, игра или пользовательский тип.
- `ItemStatus` — текущий статус: запланировано, в процессе, завершено, брошено либо пользовательский статус.
- `RefreshToken` — сохранённый хеш refresh-токена для авторизации.

## CRUD

Для `Item` реализованы `POST`, `GET`, `PUT`, `DELETE` маршруты.
Фронтенд использует эти маршруты для создания, отображения, редактирования и удаления элементов. Типы и статусы также можно создавать, получать и удалять.

## Соответствие методологии 12 факторов

### 1. Кодовая база

Один Git-репозиторий, один Go-модуль. В репозитории находятся бэкенд, фронтенд, Docker-конфигурация и миграции базы
данных.

### 2. Зависимости

Зависимости явно зафиксированы в go.mod и go.sum. Dockerfile создаёт изолированное окружение сборки на базе образа Go.

### 3. Конфигурация

Настройки, которые меняются между окружениями, передаются через переменные окружения: настройки подключения к PostgreSQL, HTTP-порт и секрет JWT. При локальном запуске значения можно хранить в файле `.env`. в репозитории есть шаблон `.env.example`.

### 4. Сторонние сервисы

PostgreSQL — внешний, подключаемый ресурс. Бэкенд получает адрес, порт, имя базы, пользователя и пароль через переменные окружения.

### 5. Сборка, релиз, запуск

Dockerfile разделяет сборку и запуск приложения: сначала код на Go компилируется в бинарный файл, затем он копируется в финальный образ Alpine и запускается командой `./catalogio`. Конфигурация передаётся контейнеру при запуске через переменные окружения, без изменения исходного кода.

### 6. Процессы.

Бэкенд является stateless-процессом. Данные каталога, пользователи и refresh-токены хранятся во внешнем сервисе PostgreSQL, а не в памяти процесса или локальных файлах. Поэтому бэкенд можно перезапустить без потери пользовательских данных.

### 7. Привязка портов.

Приложение запускает HTTP-сервер на Go и слушает порт из переменной окружения `SERVER_PORT`. Docker Compose публикует этот порт через `ports`, поэтому к приложению можно обращаться по сети.

### 8. Параллелизм.

Основной тип процесса приложения — web-процесс, который обрабатывает HTTP-запросы. Фоновые задачи и задачи по расписанию в текущей версии отсутствуют, поэтому отдельные worker- и cron-процессы не требуются.

### 9. Утилизируемость.

Приложение корректно обрабатывает сигналы SIGTERM и SIGINT. При получении сигнала сервер перестаёт принимать новые запросы и завершает текущие через server.Shutdown() с таймаутом 10 секунд.

После завершения работы закрывается пул соединений PostgreSQL. Это позволяет безопасно перезапускать или останавливать контейнер приложения.

### 10. Паритет разработки и продакшена.

Для локальной разработки и развёртывания используется одинаковый стек: бэкенд на Go, PostgreSQL, Docker и миграции базы данных. Docker Compose позволяет запускать бэкенд, базу данных и миграции в контейнерах.

### 11. Логирование.

Приложение выводит логи в стандартный поток вывода stdout с помощью пакета log. Оно не создаёт и не управляет локальными файлами логов.

### 12. Административные задачи.

Миграции базы данных выполняются отдельным одноразовым процессом migrate. SQL-миграции хранятся в директории migrations/ вместе с исходным кодом.
